## Context

根據 `proposal.md` 所述，購物車商品數量調整時存在庫存同步失效與超賣風險問題。本設計文件說明如何實現庫存即時同步與庫存上限檢查的技術方案。

## Goals / Non-Goals

**Goals:**
- 建立購物車與庫存之間的雙向即時同步機制
- 在增加商品數量前執行庫存上限驗證
- 提供清晰的 UI 反饋訊息給使用者
- 確保狀態管理層正確維護購物車與庫存資料的一致性

**Non-Goals:**
- 不修改現有的結帳流程（由 `pos-checkout` spec 規範）
- 不改變商品資料結構或 API 介面
- 不涉及遠端庫存服務整合（僅處理本地庫存邏輯）

## Decisions

### 1. 庫存同步策略：即時更新 vs 批次更新

**選擇：即時更新**

**Rationale:** 購物車操作需要即時反饋，使用者期望點擊 +/- 按鈕後立即看到庫存變化。

**Alternatives Considered:**
- **批次更新**: 在結帳時一併處理庫存扣減
  - *優點*: 減少 API 呼叫次數
  - *缺點*: 無法即時反映庫存狀態，不符合購物車即時反饋的需求

### 2. 庫存檢查時機：增加前 vs 增加後

**選擇：增加前檢查（Pre-check）**

**Rationale:** 在允許增加數量前驗證庫存可避免不一致狀態。若先增加再檢查，需要回滾機制處理失敗案例。

**Alternatives Considered:**
- **增加後檢查**: 先增加數量再驗證庫存
  - *優點*: 邏輯簡單
  - *缺點*: 需要複雜的回滾機制，可能導致短暫的不一致狀態

### 3. 狀態管理架構：單一來源真理（Single Source of Truth）

**選擇：購物車與庫存共用同一份資料來源**

**Rationale:** 避免購物車數量與庫存數量脫節，確保任何一方的變更都會反映到另一方。

**Alternatives Considered:**
- **獨立狀態**: 購物車維護自己的數量，結帳時再同步到庫存
  - *優點*: 購物車操作更快速
  - *缺點*: 需要額外的同步邏輯，容易產生不一致

### 4. UI 反饋機制：即時提示 vs 彈窗確認

**選擇：即時提示（Toast/Inline Message）**

**Rationale:** 庫存不足是常見情況，短暫的提示訊息不會打斷使用者流程。

**Alternatives Considered:**
- **彈窗確認**: 庫存不足時跳出對話框要求確認
  - *優點*: 明確告知問題
  - *缺點*: 中斷使用者流程，體驗較差

## Risks / Trade-offs

[Risk] 狀態同步延遲導致短暫的不一致顯示
→ **Mitigation**: 使用防抖（debounce）機制避免過度頻繁的更新，確保 UI 渲染與資料層同步

[Risk] 庫存檢查邏輯分散在不同元件中
→ **Mitigation**: 將庫存檢查邏輯抽取為獨立的 service/hook，集中維護

[Risk] 測試覆蓋不足導致邊界條件遺漏
→ **Mitigation**: 針對庫存邊界值（0、1、max）撰寫單元測試
